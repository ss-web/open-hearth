# Алгоритм распределения

Нормативная реализация — `shared/lottery.ts`, константы — `shared/policy.ts`. Имя версии: `hearth-quota-1`.

Ниже три отклонённых или запасных схемы и одна действующая. Запасные не считаются тайным вторым режимом: если фонд когда-нибудь сменит схему, он публикует новую версию и не переигрывает открытый раунд.

## Когда какая схема

На утро раунда:

```
баланс = поступления до этой даты − расходы до этой даты − уже сделанные выплаты
резерв = min(баланс, max(5000, floor(баланс / 10)))
доступно = баланс − резерв
```

Если сумма одобренных заявок меньше или равна `доступно`, платят всех по дате одобрения. Это обычная очередь. Жребий не нужен, и десятая доля «на следующий месяц» не отрезается: людей не заставляют ждать, когда денег хватает.

Если сумма больше `доступно`, включается жеребьёвка.

## Вариант A. Чистая очередь

Платить строго по дате одобрения, пока деньги не кончатся. Прозрачно и жестоко к тем, кто подал позже: при постоянной нехватке хвост может не двигаться месяцами. Поэтому очередь остаётся только для случая, когда хватает на всех.

## Вариант B. Чистая лотерея

У каждой одобренной заявки равный шанс, независимо от стажа, числа детей и страны. Легко объяснить, но шкала сама повышена для следующих детей, а равный жребий это не учитывает. Семья, которая ждёт дольше, не получает ничего за ожидание. Вариант оставлен как мерило: его можно посчитать тем же кодом, если всем весам присвоить 1000 и убрать приоритетную дорожку. Действующим он не выбран.

## Вариант C. Только веса, без квоты

Один взвешенный список на весь пул. Стаж, многодетность, беда и ожидание влияют на частоту, но тяжёлая ситуация может ни разу не попасть в небольшой раунд. Квота это страхует, поэтому выбран вариант D, а не чистые веса.

## Вариант D. Квота и взвешенная жеребьёвка

Это `hearth-quota-1`.

```
пул = floor(доступно * 9 / 10)
непрерывность = доступно − пул
приоритет = floor(пул / 5)
```

Непрерывность не уходит на отдельный счёт. Это потолок того, сколько можно назначить в этом раунде, чтобы следующий месяц не открывался пустым.

Приоритетная дорожка доступна заявке, если ребёнок четвёртый или дальше в этом браке, либо заявлена тяжёлая ситуация. Бюджет дорожки — `приоритет`. Кто не поместился или не был выбран, остаётся в общей дорожке. Неистраченный приоритетный бюджет прибавляется к общей.

Общая дорожка — все ещё не выбранные, бюджет равен `пул − уже назначено на приоритетной`.

В обеих дорожках одна церковь получает не больше двух выплат за весь раунд. Лимит общий, а не по дорожке.

Жадный проход идёт по взвешенному порядку. Если заявка не влезает в остаток бюджета, её пропускают и смотрят следующую. Это не укладка рюкзака: оптимальная упаковка сумм была бы менее понятна и систематически отодвигала бы крупные семьи, ради которых шкала как раз повышена. Неистраченный остаток пула остаётся в фонде.

### Вес

Считается в целых тысячных, затем показывается как тысячные / 1000.

```
стаж      = min(750, max(0, годы − 1) * 150)
семья     = 500, если порядок ≥ 4; 250, если порядок = 3; иначе 0
беда      = 350, если есть второе ходатайство; иначе 0
ожидание  = min(300, полные месяцы от одобрения до даты раунда * 50)
тысячные  = 1000 + стаж + семья + беда + ожидание
если региональный коэффициент: тысячные = round(тысячные * 12 / 10)
```

Региональный коэффициент включается для страны, только если:

- прошлых выплат уже не меньше трёх;
- в этой очереди у страны не меньше двух заявок;
- доля заявок ≥ доля прошлых выплат + 0,10.

Это защита от того, чтобы одна страна надолго забирала почти все выплаты. Это не надбавка «своим».

### Случайный порядок

Взвешенный выбор без возвращения, целыми числами.

Пока в дорожке есть заявки:

1. `сумма` = сумма их тысячных.
2. Из HMAC-SHA256(сид, ярлык шага) берётся целое в диапазоне `[0, сумма)`. Смещение по модулю снимается отбраковкой: значения, которые не укладываются в целое число корзин, отбрасываются.
3. Заявка, в чью корзину попало число, выходит из пула.
4. Её берут, если не исчерпан лимит церкви и сумма влезает в бюджет дорожки. Иначе в следе пишется причина `church_cap` или `budget`.

Ярлыки шагов разные: `priority:pick:0`, `open:pick:0`. Один и тот же сид не смешивает дорожки.

Сид:

```
SHA-256(
  hearth-quota-1
  <номер раунда>
  <значение энтропии>
  <хэш очереди>
)
```

Хэш очереди — SHA-256 канонического JSON заявок, отсортированных по номеру. Внутри уже посчитанные вес, региональный флаг и месяцы ожидания. Ключи JSON фиксированы, чтобы два языка считали один хэш.

### Порядок публикации

1. Очередь замораживают и публикуют хэш.
2. Заранее называют будущий источник энтропии: высота блока Bitcoin или номер раунда drand, которых ещё нет.
3. Когда значение появилось, из него и хэша получают сид.
4. Проводят дорожки и публикуют след: шаг, сумма весов, выпавшее число, заявка, решение.
5. Любой повторяет расчёт. Кнопка на странице раунда вызывает тот же `runRound`.

Учебные раунды помечают источник энтропии как `demo`. Будущий раунд без энтропии победителей не назначает. Учебный прогон рядом подписан как нерезультат.

## Что сознательно не входит

- Ручная внеочередная выплата. Любой такой рычаг незаметен в отчёте и ломает доверие сильнее, чем жёсткое правило.
- Проверка дохода семьи фондом. Её трудно сделать одинаково честной в разных странах; категорию беды подтверждают два пастора.
- Приоритет «сначала маленькие суммы, чтобы помочь большему числу семей». Это тихо наказывает тех, для кого шкала выше.
- Национальная льгота. Есть только выравнивание, и только при заметном перекосе.
- Смена формулы посередине раунда.

## Учебный реестр

`npm run verify` строит снимок из `shared/ledger.ts`, проверяет тождество казны и заново проводит сентябрьский раунд и учебный прогон ноября. Совпадение списка, хэша, сида и следа — условие прохождения.
